# Chat rendering: rich replies

`web/rich.js` and `web/rich.css` (shared by the desktop app and the phone page) turn a few fenced blocks and
markdown forms into app-like chat elements. Everything that reaches HTML is escaped, and URLs go through an
allowlist.

| Form | Result |
|------|--------|
| ` ```swatch ` with `- name:`, `hex:`, `note:` items | one big color chip, or a palette row for 2 to 4 colors (more than 4 are dropped) |
| ` ```cards ` with `- title:`, `url:`, `image:`, `price:`, `badge:`, `note:` items | product / link cards |
| `![caption](url)` | inline image |
| `- [ ] item` / `- [x] item` | tickable checklist (state kept in the browser) |

Images: `/api/attachments/<id>` loads directly. A remote `http(s)` image is click-to-load, because the URL could
carry data out. To show a real photo without that click, the model calls `show_image` (`docs/TOOLS.md`), which
stores the picture server side and returns an `/api/attachments/<id>` markdown line; a card `image:` may be such
an id too.

## Teaching the model

`rich_output_prompt()` (`src/agent/agent.cpp`) is appended to the system prompt of **chat and cowork** sessions.
It is kept short and imperative with one tiny example per block, because mid-size local models skip long
instructions. Its rules: naming or picking a color always includes a `swatch` block; "show me" and "what does X
look like" mean `web_search` with category `images` plus `show_image`, never images generated by code; product
and link lists use `cards`; never write scratch files into the home directory to make visuals.
`tests/test_show_image.cpp` checks that the examples are present.
